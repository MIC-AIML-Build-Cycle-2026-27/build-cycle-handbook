# Overview

## What is the Build Cycle?

The **MIC AIML Build Cycle 2026-27** is the AIML Department's project cycle under the **Microsoft Innovation Club (MIC)**. From **6 October 2026 to 30 January 2027**, students work in project teams to build real AI, ML and software systems. That means doing the research, implementation, experimentation, testing, documentation and evaluation that real systems need.

The goal is to build something that works, and to learn how engineering and research are done in practice along the way: working from issues, reviewing each other's code, measuring results honestly and documenting what you did.

## The projects

| # | Project | Summary |
|---|---|---|
| 1 | **ONS**: Operations Nervous System | An AI system for freight operations that works with shipping documents and carrier data to track shipments, identify risks, and help operations teams act before problems occur. |
| 2 | **ASRA**: Autonomous Scientific Research Agent | An AI research agent that can find papers, analyse evidence, identify research gaps, validate claims, and run experiments in a controlled environment. |
| 3 | **PRISM**: Property Recommendation & Interior Space Matcher | An AI-powered property platform that learns what users are looking for, recommends suitable properties, analyses interiors, and helps visualise furniture and spaces. |
| 4 | **Repository Fixer** | An AI coding agent that can analyse issues in a repository, generate fixes, and test those fixes in an isolated environment before they are proposed. |
| 5 | **Hallucination Scorer** | A project focused on evaluating and scoring hallucinations in AI-generated responses. |
| 6 | **Code Evolver** | An AI system that analyses a GitHub repository and suggests different ways the codebase could be evolved based on a developer's objective, while testing and comparing the possible approaches. |
| 7A | **DLD Screening**: Developmental Language Disorder Screening | An AI/ML-based screening system that analyses speech and language responses, extracts relevant features, and produces a screening profile for further review. |
| 7B | **Software Investigator** | A system that can simulate software failures, collect logs and telemetry, and use that information to investigate and identify possible root causes. |

Each project has its own repository, team and project board. See the [organisation page](https://github.com/MIC-AIML-Build-Cycle-2026-27) for links.

## How it works

```
Foundation → Proof of Concept → Core Build → MVP → Integration & Evaluation → Finalisation
             └──── Review 1 ────┘            └ Review 2 ┘                     └ Final Review ┘
```

- **Three reviews** mark progress: [Review 1](review-1.md) (POC), [Review 2](review-2.md) (MVP) and the [Final Review](final-review.md) (complete system, evaluation and demo). Dates are in the [Timeline](timeline.md).
- **Project Leads** (two per team) guide and coordinate the team. They split work into tasks, track progress and unblock people. They are not expected to build the project themselves. See the [Project Lead Guide](project-lead-guide.md).
- **Team members** pick up issues, build, test, document and review each other's work.
- **Department Leads** run the cycle as a whole, organise reviews and maintain this handbook.

## Principles

1. **Build something real.** A small system that works end to end beats a large one that only exists in slides.
2. **Everyone contributes and learns.** Work is divided so every member owns something meaningful.
3. **Work in the open.** Use issues, pull requests and the project board, so anyone can see what is happening and why.
4. **Measure honestly.** Results need a method behind them. A clear negative result is more useful than an inflated positive one.
5. **Document as you go.** If it is not written down, the next person cannot build on it.
6. **Keep process light.** Structure should help students build, not get in the way of building.
